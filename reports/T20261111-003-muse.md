## 架构评审

### 1. 商品三层模型（标准款式 → 规格版本 → 来源图片/群消息）：成立，需补两点
- “相似不等于同款”须落成人工确认与纠错闭环：向量召回只给候选，标准款归属须留置信度字段与人工复核记录，否则误并款会污染整库。
- 规格 Variant 必须把“同形状不同规格不混并”写进唯一性规则：款式 ID + 圈口/克重范围/工艺/材质共同决定一条规格，报价与库存只挂在规格及商家上架层，不挂在款式层。

### 2. 本地数据层：方向对，规模处须实测
- 原图与索引分离、SHA256 + 感知哈希 + OCR + 向量 embedding 的字段设计合理。
- 50 万图规模下，SQLite 单库 + FTS 需做性能基准：建议 Buddy 实测索引构建时间、单图入库耗时、向量召回 P50/P95 延迟；若 SQLite 向量检索吃力，评估 sqlite-vec 或 FAISS 边车，不要直接上重型搜索引擎。
- 微信 CRI 能力、权限与兼容性一律先验证、不假设：多微信实例检测、账号身份确认、手动/选定/定时增量三种同步模式，都须以实测为准。

### 3. 本地 / 云端 / Supabase 取舍：分阶段，不仓促迁移
- 阶段一（现在）：本地优先。原图、微信同步、索引全在本地；Git 只做任务与脱敏报告。
- 阶段二（内部验证后）：Supabase 可作 Postgres + Auth + Storage + pgvector 候选，承接账户、租户隔离、标准产品库、授权缩略图与查询索引；原图仍本地优先。
- 不建议：为调度而迁云；把 Git 当图片/客户数据库；云端未做鉴权、审计、加密、删除与成本预算就同步数据。
- 成本对比（本地 / Supabase / 自建后端 / 对象存储+CDN）须出实数：存储量、带宽、向量查询量、月费上限与告警线，待 Buddy 盘点数据量后才能算。

### 4. 轮询与即时调用可行性
- 现有唯一可靠通道是 GitHub 文件轮询（Muse 每 15 分钟读 `tasks/inbox/`）。Muse 无公开 inbound API / Webhook / MCP 入口，不能被直接调用；WorkBuddy 本地代理尚未接入轮询，端到端未完成。
- 即时触发目前无已授权途径：GitHub Webhook 需公网可达端点，本地 Windows 机器无此条件；不要假设可直调 Muse / WorkBuddy 智能体本体。
- 最小风险快速通道：轻量脚本（gh CLI / API）高频探查 inbox 变更，有新文件才唤起模型；模型轮询保持 15 分钟或放宽。不要用缩短模型轮询间隔来换速度。

### 5. 与 Buddy 方案的冲突点（待 Buddy 回写后逐项比对）
- 本地数据层选型：SQLite vs 搜索引擎 vs 向量库边车。
- 云端阶段划分：何时引入 Supabase、哪些数据上云、租户隔离怎么做。
- 微信同步范围：哪些账号/群可读、读取频率与账号风控边界。
- 50 万图处理策略：全量索引 vs 抽样先行（总纲要求非破坏性抽样与规模评估，禁止缩减为 1000 图重做）。
- 宣传模块生图边界：AI 生成图是否可用于真实商品展示（总纲要求校验款式、重量、工艺不被改动）。
