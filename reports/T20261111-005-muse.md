## 一、关系层接口与数据契约复核（针对 004-Buddy §2.1 设计）

结论：五张表（style / variant / store / listing / source）的设计成立，可直接作为 SQLite 起步实现与云端迁移契约。以下改进点均可在不改原索引、不动原库的前提下并行合并。

### 1.1 逐表复核意见

| 表 | 复核意见 |
|---|---|
| style | 成立。须补三点：① `canon_img` 只存授权标准图 ID，另加 `canon_img_license` 字段记授权来源/范围；② `status='merged'` 时须有 `merged_into` 字段指向目标 style_id，否则合并不可追溯、不可撤销；③ 版本变更须留痕，建议加 `style_history(style_id, version, change_note, changed_at)`，不只靠 `version` 数字自增。 |
| variant | 成立。须加规格唯一性约束：`UNIQUE(style_id, size_mm, ring_size, weight_g_min, weight_g_max, craft, material)`，否则同一规格可重复建两条。同形状不同规格绝不混并的铁律靠约束落地，不靠人工自觉。 |
| store | 成立。认领状态机 `unclaimed → claimed → verified → revoked` 成立，须补：① `claimed` 与 `verified` 之间必须经过平台审核（不能商家自填即 verified）；② `license_no`（营业执照号）不得随店铺公开信息出库，须单独权限字段/分表；③ `geo_license` 为空时该店坐标与名称不得对外展示（004-Buddy 铁律 1 的落表形式）。 |
| listing | 成立。须补三点：① 报价分层要写清：variant 层只挂厂家参考价/指导价区间，商家实际报价只挂 `listing.price`，两处价格不得互相覆盖；② `price_updated_at` 超 3 天对外展示「信息可能过期」，须落成展示规则而非口头约定；③ 建议加 `listing_history` 快照表（改价/改库存即写一条），首版可先只记 `price` 与 `stock_status` 变更。 |
| source | 成立。须补：① `confidence` 阈值须定值后写进迁移脚本注释（建议 0.8，低于阈值进人工复核队列、不进已发布状态）；② `origin_ref` 只存溯源索引编号，不存原始链接/群消息原文；③ 证据保留期限须定值（建议至少保留至 listing 下架后 180 天，过期脱敏归档）。 |

### 1.2 通用契约补强（五张表共用）

1. 每张表补 `created_at` / `updated_at`（variant 表目前缺失）；`updated_at` 由写入方统一维护，增量同步以它为准。
2. 迁移脚本必须幂等：`CREATE TABLE IF NOT EXISTS` + 按自然键 `INSERT … ON CONFLICT DO NOTHING/UPDATE`；重跑不得产生重复 style/variant/listing；迁移脚本本身带版本号（如 `migrate_001_style.sql`），按编号顺序执行。
3. 开启 `PRAGMA foreign_keys=ON`；`listing.variant_id` 可空（商家未填规格时），但 `store_id` / `style_id` 不可空。
4. 索引（首版最小集）：`listing(style_id, publish_state)`、`listing(store_id)`、`source(target_kind, target_id)`、`variant(style_id)`。向量字段 `shape_vec` 首版可为空，不阻塞建表。
5. 误合并纠错：style 合并必须是可逆操作——合并只改 `status` 与 `merged_into`，不删除被合并行、不改 variant 外键指向；撤销即恢复状态。

### 1.3 可并行合并的改进包（与 004-Buddy P1–P9 对齐）

| 包 | 内容 | 依赖 | 冲突避免 |
|---|---|---|---|
| M1 | style 主键化迁移脚本 + `merged_into` / `style_history` | 无 | 只动新增表，不动原索引 |
| M2 | variant 抽取 + 唯一性约束 | M1 | 先跑 M1 生成 style_id 再抽取 |
| M3 | 998 条未命中造型归类补充 | 无 | 只写新表，不改分类引擎 |
| M4 | store / listing 状态机 + `listing_history` | M1 | 与 M2 不同表，可并行 |
| M5 | source 置信度阈值 + 人工复核队列表 | 无 | 纯新增表 |
| M6 | 宣传流程状态机 + 成本台账字段 | 无 | 纯新增表 |

合并规则：Buddy 与 Muse 不同时改同一文件；每项变更附测试、回滚方式、完成状态、下一步（任务卡要求）；任一包失败只回滚该包，不动其他包。

## 三、宣传 8 步链路（状态机版）

`选品 → 趋势研究 → 创意/文案 → 素材制作 → 人工审核 → 发布 → 数据反馈 → 归档复盘`

| 步 | 输入 | 输出 | 负责人 | 成本字段 | 审核点 |
|---|---|---|---|---|---|
| 1 选品 | style_id / listing_id | 选题单（款式 + 卖点 + 金价） | Muse/Buddy | 无 | 款式须为授权标准图或商家实物图 |
| 2 趋势研究 | 关键词/对标账号 | 趋势简报（来源 URL 存档） | Muse（Just One） | Just One 调用次数 × 单价 | 只读数据，不下载他人素材 |
| 3 创意/文案 | 选题单 + 趋势简报 | 文案稿（400 字左右，生活化） | Muse | 无 | 不写「店里有货/现货」；软钩子按既定口径 |
| 4 素材制作 | 文案稿 + 授权商品图 | 成品图/视频 | Buddy（豆包/Seedance） | 生图张数 × 单价 / 视频秒数 × 单价 | AI 不得改动款式结构、比例、克重、工艺 |
| 5 人工审核 | 成品 + 来源清单 | 通过 / 驳回（留痕） | 用户/人工 | 无 | 素材来源字段齐全；来客渠道须合规版（无秒杀/限时/站外引导语） |
| 6 发布 | 审核通过的成品 | 发布回执（平台 + 时间 + 链接） | 一小二（待核验） | 平台费用 | 只发测试/草稿须注明；真实发布须用户批准 |
| 7 数据反馈 | 发布回执 | 阅读/互动/转化回收表 | Buddy | 无 | 回收数据只记汇总，不存用户隐私 |
| 8 归档复盘 | 全链路记录 | 复盘条目（成本/效果/改进） | Muse | 单条总成本 | 成本超预算即告警 |

硬边界：不充值、不批量生成、不对外发布，均须用户批准；每步状态变更写表，不只靠聊天记录。

## 四、商家认领流程（状态机版）

```
地图/搜索命中 → 店铺页（unclaimed，仅公开信息，须 geo_license 非空才显示）
  → 商家提交认领（营业执照 / 门店照 / 手机验证）
  → 平台审核（通过 → claimed；驳回 → 注明原因，可重提）
  → 商家补资质 → 平台验证（通过 → verified；失败 → claimed）
  → 店铺后台按类目/造型浏览标准款 → 勾选「我有这款」
  → 补录实际克重、圈口、工艺、可售状态、报价、实物图
  → 提交 → 平台审核（publish_state: review → published / 驳回）
  → 消费者/同行按款式或地图查询 → 看到哪家店有这款、什么克重、什么价、什么时候更新
  → 商家可撤销上架（unpublished）/ 注销认领（revoked，须平台确认）
```

规则：
- POI 发现数据与商家主动提交数据分字段存放；批量导入**不允许**创建未认领店铺。
- 报价/库存只来自商家自填或授权同步；超 3 天未更新对外显示「信息可能过期」并附最后更新时间。
- 首版只做自家福珑珠宝与金大福两家示范店；随后邀约商家自愿入驻，不自动替全国 POI 建立冒名店铺。
- 撤销/删除须留痕：listing 下架保留历史快照；store 注销保留认领记录（脱敏后归档）。

## 五、云端迁移条件与 Supabase 成本评估（只评估，不创建收费资源）

### 5.1 Supabase 公开价格（2026 年 10–11 月口径，以 supabase.com/pricing 实时页为准）

| 项 | Free（$0/月） | Pro（$25/月起） |
|---|---|---|
| 数据库 | 500 MB/项目 | 8 GB/项目，超量 $0.125/GB/月 |
| 文件存储 | 1 GB | 100 GB，超量 $0.0213/GB/月 |

| 其他 | 闲置 1 周自动暂停；限 2 个活跃项目 | 不暂停；多项目 $10/月起 |

### 5.2 按现有规模匡算

现有资产：前端 119 MB、图片索引 47 MB、字段索引 10.1 MB、去重索引 9.7 MB、溯源索引 59,267 条。结构化数据（style/variant/store/listing/source 五张表 + 授权缩略图）量级在数百 MB 以内，**Pro 免费额度内可装下**；原图（约 50 万张口述规模）**不进云**，只放授权缩略图。首年 Pro 成本区间约 $25–35/月（$25 基础 + 少量超量），以实际用量为准；Free 档可用于迁移演练，但闲置暂停与 500 MB 上限不适合生产。

### 5.3 迁移前置条件（缺一不可，全部满足前不迁移）

1. 租户隔离：Row Level Security（RLS）按 store/merchant 隔离；商家只能读写自家 listing。
2. 权限与审核：认领验证、发布审核、删除权限三条流程先在本地跑通再上云。
3. 删除与数据可携带：商家可导出自家全部数据、可请求删除；删除须级联 listing 与 source 记录并留审计日志。
4. 审计与加密：写操作留审计表；敏感字段（license_no、phone）加密存储、不进公开接口。
5. 成本上限与告警：设月度预算与超量告警；Spend Cap 开启；超预算即暂停非关键同步。
6. 备份与回滚：迁移前本地全量备份；迁移脚本可回滚；云端数据可完整导回本地。
7. 脱敏：客户私聊、联系人、微信原始内容、原图、凭据绝不上云；Git 只放方案与脱敏报告。

结论：本地优先不变；Supabase 为阶段二候选，迁移是「条件触发」不是「时间触发」。
