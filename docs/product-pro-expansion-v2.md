# Product Pro 全局补充方案 v2 — 供应链地图、商家开店与营销闭环
日期：2026-11-11。与 docs/product-pro-master-plan-v1.md 并行阅读，v1仍有效。此文是用户目标，不代表所有功能已经验证。

## 核心定位
全国黄金珠宝行业的“标准款式库 + 商家店铺网络 + 智能找货 + AI营销”。不是简单地图黄页，而是让每家商户认领/创建自己的线上店，勾选平台标准款并录入自家规格、重量、报价、库存、实物图，形成可检索的供应网络。参考酷家乐“标准模型库”式产品组织，但不要照搬其授权资产。

## 四层数据模型
- 标准款式 Style：平台唯一款式ID、类别（八宝罗盘、葫芦、素圈、四叶草等）、结构/工艺/材质特征、授权标准图、向量索引、版本。
- SKU/规格 Variant：尺寸、圈口、克重范围、工艺、材质、品牌授权信息；同形状不同规格不混并。
- 商家 Merchant/Store：店铺ID、店名、可公开的经营地址、坐标、联系方式、认证状态、营业资质、地理数据来源与授权。
- 商家上架 Listing：store_id + style_id + variant_id，商家实物图、实际克重、可售状态、报价、更新时间、来源与证据。一个款可有多商家；一个商家可有多款。库存/价格是商家自行维护或授权同步，不可从地图POI推断。
- Source/Offer：厂家群图片、供应商报价及时间、原始证据、授权范围，关联标准款和店铺时需保留置信度与人工纠错。

## 体验路径
地图搜索珠宝商家→商家认领并验证身份→开通店铺→选择标准款式（支持按图检索/分类）→勾选“我有这款”→补录重量/规格/库存/图片/价格→发布→消费者/同行按款式或地图查询→联系商家核实。平台支持商家批量导入和增量更新；店铺三天未更新仅提示信息可能过期。
首版先做自家福珑珠宝和金大福的示范店、标准款映射及供货商查询；随后邀约商家自愿入驻，不自动替全国POI建立冒名店铺。

## 地图/商家数据策略
用户称本地已采集全国黄金珠宝门店地址、电话、坐标，百度报价约5万元。Buddy应先做只读盘点：数据来源、协议、调用方式、存储与展示权、缓存期限、商业使用限制、是否允许再分发、数据质量及去重。保留既有代码和合法可保留资产；不得因为本地已有数据就推断有永久商业化使用权。必要时切换有授权的POI服务、商家自主入驻、公开许可数据或自建商家库；不能通过绕过配额/付费限制规避合同。

## AI宣传中心（已有能力优先复用）
用户称Muse已接一小二，可结合产品和金价执行发布；Just One用于小红书/抖音趋势研究；Seedance/豆包等用于图视频生成，部分账号可能欠费。Buddy与Muse盘点现有接口、已验证流程、余额与调用日志（只报脱敏统计），建立“选产品→趋势研究→创意/文案→使用授权商品图制作素材→人工审核→一小二等平台发布→数据反馈”工作流。不要将他人爆款素材简单洗图后当原创发布；仅使用有权使用的素材，保留产品结构、尺寸和纹理，不得虚构克重和品牌授权。先评估图像理解/编辑/生成/视频分别的单位成本，欠费不自动充值。

## 体系架构与云
本地代理负责微信/本地图片，原图本地优先；云端负责商家身份、店铺目录、标准款式ID、授权缩略图、查询索引、同步日志。多租户隔离、权限、审核、删除和数据可携带性为商业化前提。Supabase可作为Postgres/Auth/Storage/向量服务候选；Git仍只做任务、代码、脱敏报告，不当图片/客户数据库。对比本地、Supabase、自建后端、对象存储/CDN的成本、延迟与带宽，提出阶段选择。
AI角色：ChatGPT产品统筹；Buddy本地工程与集成；Muse架构研究、营销接入及建议。通过Git异步任务与回写协作；不可把Git提交等同于Muse/Buddy已领取。

## 验收指标
1. 现有项目复用率和真实数据规模（用户称约50万图、4万客户，待核验）。
2. 标准款式→规格→商家上架映射准确率及纠错成本。
3. 商家认领/授权/上架、可撤销、可更新、可删除。
4. 图片找款/找商家检索延迟与覆盖率；多商家报价时间透明。
5. 既有营销接入的可用性、每条内容成本、审核后发布成功率。
6. 地图数据许可风险、云带宽/存储预算与阶段性商业可行性。
## 安全边界
公开Git只放方案、匿名汇总与无敏感内容的任务。未经批准不读取/上传客户私聊、完整联系人、地图批量数据、原图、凭据；不自动开店、对外发布、充值、签约、删除、部署或开放网络端口。
